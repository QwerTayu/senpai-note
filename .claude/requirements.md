# senpai-note 要件定義

Built with Claude: Japan 2026（テーマ1「あなたにしかない深さを。」）の応募作品。
提出は 2026/11/08(日) 13:00 を目標にする（公式の締切は 20:00、15:00 以降は作業できない）。

## 解く問題

長岡技術科学大学は、多くの学生が B3 で入学する（入学1年目が B3）。技大祭実行委員会の1年は次のように回る（総務局の Slack 1年分、2025/10〜2026/11 で確かめた）。

| 時期 | 出来事 |
|---|---|
| 4月 | B3 が入学し、部門員になる |
| 9月初め | 次の代の局長（B3）が決まる |
| 9月中旬 | 技大祭の本番 |
| 9月下旬 | 部門長の引き継ぎ会。B3 が次の代の部門長になる |
| 10月〜2月 | B4 は実務訓練で学校を離れる。新しい部門長は入学して半年で、年間計画などを始める |
| 4月〜 | 前の代が M1 として戻り、「新旧部門長」チャンネルで相談役になる |

**一番困るのは10月〜2月**。新しい部門長が一番聞きたい時期に、前の代は実務訓練でいない。連絡はつくが返事は遅い（実例: 5/1 の質問に 5/6 に返信）。前の代が戻ったあとも、相談は「新旧部門長」チャンネルでの手作業で、そのやりとりは翌年に残らない。総務局では内製アプリ GroupManager（GM）への要望も毎年変わる。

前の代の答えには、手順だけでなく、時期・理由・例外・過去の指摘が入っている（例:「去年は7月第3週に出店場所を確定していた（看板の発注に間に合わせるため）」「ある建物は予約不要。ただし本番中に誰がどこにいるかを把握するため部屋は一覧にする」「去年、顧問の先生から届けの書き方について指摘があった」）。これが人の頭とチャンネルにしか残らない。

一般化すると、「毎年メンバーが入れ替わり、経験者がすぐいなくなる組織」の問題になる（学生団体、PTA、町内会など）。

## コンセプト

B4 に引き継ぎのための時間を取らせない。そのうえで、**B4 が直接いなくても B3 の代が回るように、アプリが「先輩の代わり」をする**。聞かれたら答えるだけでなく、先輩のほうから「今はこれをやる時期。去年はこうして、こういう問題があったから、今年はこうするといい」と示す。

1. **ためる**: ふだんのやりとり（Slack・Drive・Notion）から、エージェントが「何を、いつ、なぜそう決めたか」を知識カードにする
2. **確かめる**: B4 はカードに ✅ を押すか、カードごとにエージェントと会話して直すだけ
3. **答える**: 新しい代の質問に、確認済みのカードから元の投稿を示して答える
4. **抜けだけ聞く**: 記録にないことは、エージェントが「先輩への質問」にまとめる。実務訓練中の B4 が遅れて返事をすると、その答えがカードになる
5. **先輩の代わりに導く**: 今年の本番の日を入れると、エージェントが確認済みのカードから今年の年間計画を作る。計画の項目ごとに、去年の問題とアドバイスを付ける。B3 は計画を今年のものとして直し（日付・完了・メモ・項目の追加と削除）、その記録が次の代の知識の元になる

聞かれて答えるだけの RAG にはしない（ガイドの禁止例）。売りは 1・4・5 で、知識が増えていく流れ、先輩の負担が小さいこと、先輩がいなくても次にやることがわかること。

アドバイスは2種類に分ける。
- **記録**: 知識カード（過去の指摘・理由・先輩の回答）に書かれていること。根拠のカードを必ず付ける
- **提案**: 記録をもとにエージェントが考えた「こうするとよい」。根拠のカードを付け、画面では「エージェントの提案」と区別して出す。先輩が ✅ すると「先輩が確認した提案」になる。先輩は違うと思えば却下でき、却下した提案は消える

口調はふつうの「です・ます」にする。先輩らしさは中身（時期・理由・去年の失敗・アドバイス）で出し、先輩になりきった話し方はしない。

やらないこと: 時期が来たら知らせるリマインド（通知はしない。「今やること」は画面を開いたときに見えるだけ）。Slack の中で確認を完結させること（確認は別のアプリで行い、取り込み元に依存しない）。

## 利用者

| 役 | 画面 | すること |
|---|---|---|
| 先輩（B4） | `/senpai` | カードの確認・修正、先輩への質問に答える、エージェントの提案を確かめる |
| 後輩（新しい代） | `/kouhai` | 今年の計画を作って直す、今やることとアドバイスを見る、質問する、カードを読む |

### 登録（最初に開いたとき）

ログインは作らないが、最初に開いたとき（合言葉のあと）に登録の画面 `/register` を出し、次を入れてもらう。登録の内容はブラウザの cookie に持ち、サーバーは誰の操作かの記録に使う。

1. 役: **現役の代**（B3。今年の本番を担当する）か、**前の代**（B4。引退して実務訓練などに出ている）か
2. 代: 担当する（した）本番の年で数える。「2027年度の代」＝2027年の本番を担当する代（2026年9月の引き継ぎ〜2027年9月）。今日の日付から、現役なら今年度の代、前の代ならその1つ前を初めから入れておく
3. 部門: 局長・会場・備品・申請。計画と知識カードを、最初から自分の部門で絞り込んで出す
4. 名前: 先輩の回答、知識カードの確認、計画の変更に「誰が」を残す（自己申告）
5. 本番の日: 現役の代で、その代の本番の日がまだ入っていないときだけ聞く（その代で最初に登録した人が入れる）。入れると、その代の年間計画を作る。2人目からは入力済みの日を見せるだけ

登録したあとは、現役は後輩の画面、前の代は先輩の画面だけを使う。画面の上部での役の切り替えはなくし、右上の設定メニューに「登録し直す」を置く（デモや共用の PC で役を変えるため）。

後輩の画面は「今年の計画」と「質問する」の2つのタブにする。計画のいちばん上に「今やること」（期限を過ぎた・30日以内の未完了の項目）を出す。計画は月ごとに並べ、担当の部門（局全体・会場・備品・申請）で絞り込める。

デモではログインを作らず、登録の画面で役を選ぶ。API キーの濫用を防ぐため、デプロイ先は簡単な合言葉（環境変数 `DEMO_PASSCODE`）で守る。

運用するときは（ハッカソンでは作らない）、Cloudflare Zero Trust のメールアドレス認証をアプリの前に置く。そのときは合言葉をやめ、登録の名前を認証したメールアドレスに結びつける。

## 技術スタック

- Next.js（App Router, TypeScript, Tailwind CSS）
- Claude API（`@anthropic-ai/sdk`、Route Handler からサーバー側でだけ呼ぶ。キーはクライアントに出さない）
- Firestore（`firebase-admin` をサーバー側で使う）
- Vercel

取り込み（カードを作る処理）だけ Managed Agents で作る。エージェントと環境は `scripts/setup-agent.ts` で一度だけ作り、ID を環境変数（`INGEST_AGENT_ID` / `INGEST_ENVIRONMENT_ID`）に入れる。`POST /api/ingest` がセッションを作り、エージェントが呼ぶカスタムツール `create_card` / `update_card` をサーバーで受けて Firestore に書く（先輩の画面の「取り込む」ボタンから動かす）。定期実行（scheduled deployments）は時間があれば足す。修正の会話・質問への回答・先輩の回答は、画面からすぐ返事が要るので Messages API のツール使用で作る。
カードは数十〜数百枚の想定なので、ベクトル検索は使わず、確認済みのカードをすべてコンテキストに入れる（プロンプトキャッシュを使う）。

## データモデル（Firestore）

### `sources/{id}` 取り込み元の投稿・資料
- `kind`: `slack` | `drive` | `notion` | `plan`（今年の代が計画に残した記録。日付を変えた理由、ふりかえりのメモ）
- `title`: string（Slack はチャンネル名、Drive・Notion は資料名、plan は「今年の計画: 項目名」）
- `author`: string
- `postedAt`: timestamp
- `url`: string（デモでは架空の URL）
- `body`: string
- `ingestedAt`: timestamp | null（取り込み済みになった時刻。未処理は null）
- `generation`: number（投稿した時期の現役の代。9月下旬の引き継ぎを境に、`postedAt` から決める。plan は記録した代）

### `cards/{id}` 知識カード
- `title`: string
- `kind`: `procedure`（手順）| `decision`（判断とその理由）| `exception`（例外の対応）| `lesson`（過去の失敗・指摘と、それを受けたやり方）| `contact`（連絡先・窓口）
- `when`: string | null（時期。例: 「7月上旬」「本番2週間前」）
- `body`: string（何をするか・何を決めたか）
- `why`: string | null（理由。わからなければ null）
- `sourceIds`: string[]（根拠の投稿。1件以上。先輩の回答から作ったカードは `answerIds`）
- `answerIds`: string[]
- `status`: `draft` | `confirmed`
- `generation`: number（どの代のやり方・知識か。根拠が複数の代にまたがるときは、いちばん新しい代。取り込みエージェントが根拠の投稿の代と中身から決める。先輩の回答から作ったカードは、答えた先輩の代）
- `confirmedBy`: string | null（確かめた先輩の名前と代。例「野口（2026年度）」）
- `createdAt`, `updatedAt`: timestamp

### `cards/{id}/messages/{id}` カードの修正の会話
- `role`: `senpai` | `agent`
- `text`: string
- `createdAt`: timestamp

### `questions/{id}` 後輩の質問
- `text`: string
- `answer`: string | null
- `citedCardIds`: string[]
- `status`: `answered` | `gap`（カードでは答えられなかった）
- `senpaiQuestionId`: string | null
- `askedBy`: string（質問した人の名前と代）
- `createdAt`: timestamp

### `senpaiQuestions/{id}` 先輩への質問（抜け）
- `text`: string（エージェントが、似た質問をまとめて短く言い直したもの）
- `questionIds`: string[]
- `status`: `open` | `answered`
- `answer`: string | null
- `cardId`: string | null（回答から作ったカード）
- `answeredBy`: string | null（答えた先輩の名前と代）
- `createdAt`, `answeredAt`: timestamp

### `generations/{年}` 代（例: `generations/2027`）
- `festivalDate`: string（その代の本番の初日。`YYYY-MM-DD`）
- `registeredBy`: string（本番の日を入れた人）
- `planStatus`: `none` | `running` | `done` | `error`（計画づくりを同時に2回動かさないため）
- `planStartedAt`: timestamp（running になった時刻。10分以上 running のままなら止まったとみなす）
- `planGeneratedAt`: timestamp | null
- `createdAt`: timestamp

### `planItems/{id}` 計画の項目（代ごと）
- `generation`: number（どの代の計画か）
- `title`: string（やること）
- `detail`: string（何をするか。知識カードの要約）
- `date`: string（今年の日付。`YYYY-MM-DD`。期間のものは始まりの日）
- `department`: `局全体` | `会場` | `備品` | `申請`
- `cardIds`: string[]（元の知識カード。B3 が足した項目は空でよい）
- `origin`: `generated` | `added`（エージェントが作った / B3 が足した）
- `done`: boolean
- `memo`: string | null（ふりかえり）
- `dateChangeReason`: string | null（日付を変えた理由。日付を変えるときは必須）
- `originalDate`: string | null（エージェントが最初に出した日付）
- `updatedBy`: string | null（最後に直した人）
- `createdAt`, `updatedAt`: timestamp

### `advice/{id}` 計画の項目へのアドバイス
- `planItemId`: string
- `generation`: number（どの代の計画へのアドバイスか）
- `kind`: `record` | `suggestion`（記録 / エージェントの提案）
- `text`: string
- `cardIds`: string[]（根拠の知識カード。1件以上）
- `status`: `confirmed` | `draft`（record は常に confirmed。suggestion は先輩が ✅ するまで draft）
- `confirmedBy`: string | null
- `createdAt`: timestamp

B3 が日付を変えた理由やメモを保存すると、`sources` に `kind: plan` の取り込み元を作る（同じ項目は上書きし、`ingestedAt` を null に戻す）。次に取り込むと、それが知識カードになり、次の代の先輩の知識になる。

## エージェント（Claude のツール使用）

| 処理 | 入力 | ツール | 出力 |
|---|---|---|---|
| 取り込み `POST /api/ingest` | 未処理の sources ＋既存のカード | `create_card`, `update_card` | draft のカード。既存のカードと重なるものは統合する |
| 修正の会話 `POST /api/cards/[id]/chat` | カード＋根拠の投稿＋会話 | `update_card`, `confirm_card` | 返信とカードの更新 |
| 質問への回答 `POST /api/questions` | 質問＋確認済みのカード | `answer`, `report_gap` | 根拠のカードを示した回答。答えられないときは先輩への質問を作るか、似た open の質問に合流させる |
| 先輩の回答 `POST /api/senpai-questions/[id]/answer` | 先輩への質問＋回答 | `create_card`, `answer_kouhai` | confirmed のカード（答えた先輩の代）。元の後輩の質問にも回答を返す |
| 計画づくり `POST /api/plan` | その代の本番の日＋確認済みのカード（代つき）＋今日の日付 | `add_plan_item`（アドバイスは項目の中に 0〜2件の配列で渡す） | 今年の計画の項目と、項目ごとのアドバイス（記録・提案）。作り直すときは、前の計画と提案を消して作る |

決まりごと:
- カードには必ず根拠（`sourceIds` か `answerIds`）を付ける。根拠のない推測でカードを作らない
- 理由がわからないカードは `why: null` にし、修正の会話で先輩に理由を尋ねる
- 回答は確認済みのカードだけを根拠にし、draft は使わない
- 複数の代のカードが食い違うときは、新しい代のやり方を正とし、古い代のやり方は「以前は〜」として扱う
- 先輩の画面では、自分の代のカードを最初に出す（ほかの代のカードは絞り込みを外すと見える）
- 計画の項目の日付は、カードの時期（「本番の6週間前」「6月中」など）を今年の本番の日から計算する。時期のないカードは計画にしない
- アドバイスの記録は、カードに書かれていることだけにする。提案はカードから考えてよいが、根拠のカードを付け、記録と混ぜない

モデルの ID とパラメータは、実装のときに claude-api skill で確かめる。

## デモ用データ

架空の「〇〇祭実行委員会 総務局」を Claude に作らせ、`data/demo/` に JSON で置く。実際の技大祭のデータはリポジトリに入れない（公開リポジトリのため）。

実際の Slack のダンプ（NUTMEG の Google Drive にある。Slack が無料プランで3か月しか残らないため）は、架空のデータの形と中身の参考にだけ使い、リポジトリの外に置く。ダンプには個人名、メールアドレス、Slack のファイル URL とアクセストークンが入っているので、文面も名前も架空のデータに写さない。

- Slack: 総務局、部門長、新旧部門長、マニュアル窓口の4チャンネルで1年分、60〜100件。前の代への「去年はどうでしたか？」と、遅れて返ってくる答えを含める
- Drive: 申請書の手順、備品の一覧など 4〜5件
- Notion: 去年の振り返りなど 2〜3件

「理由が書かれていない決定」「年によって変わったやり方」「記録にない例外」を混ぜ、抜けの処理がデモで起きるようにする。

## デモ動画（3分）の流れ

1. 問題（30秒）: 入学半年で部門長になった B3 が一番聞きたい10月〜2月に、前の代は実務訓練でいない。実際の技大祭でも、新旧部門長のチャンネルで聞いて返事を何日も待っている
2. ためる・確かめる（60秒）: ふだんの相談のやりとりを取り込むとカードができる。理由のないカードで、エージェントが先輩に理由を尋ね、先輩が答えると直る
3. 先輩の代わりに導く（50秒）: 後輩が今年の本番の日を入れると、年間計画ができる。「今やること」と、項目ごとに去年の問題とアドバイス（記録と提案）が出る。日付を変えて理由を書くと、次の代の知識の元になる
4. 答える・抜けだけ聞く（30秒）: 後輩が質問し、元の投稿を示して答えが返る。記録にない質問は先輩への質問になり、先輩が答えるとカードになって後輩に届く
5. 締め（10秒）: 毎年入れ替わる組織ならどこでも使える

## 遅れたときに削る順

1. 計画の記録を取り込み元に加える部分（次の代へのつながりは README と動画で語る）
2. 計画の項目を足す・消す（日付の変更・完了・メモは残す）
3. 提案を先輩が ✅ する画面（提案は「確認待ち」の表示だけにする）

削らない: カードを作る → 先輩が確かめる → 根拠を示して答える → 今年の計画とアドバイス。
